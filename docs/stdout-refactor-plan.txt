--------------------------------------------------------------------------------
 1. GOAL & HARD CONSTRAINTS
--------------------------------------------------------------------------------

 Goal
   Reduce a ~130-line timestamped console stream to roughly 25-30 lines of
   phase headers, status badges, aggregated loop summaries, and a final
   execution summary block. Full detail continues to flow to the file log.

 Hard constraints -- these remain COMPLETELY UNTOUCHED:

   U1. File logging targets and formats
       - $LOGFILE path:  $HOME/temp/deploy-config_<YYYYmmdd_HHMMSS>.log
       - $LOGFILE line format: [YYYY-mm-dd HH:MM:SS] [LEVEL] message
       - setup_completions' separate error_log_<timestamp>.txt file
         (same path, same per-item content).

   U2. Execution logic
       - Function bodies' commands (apt, curl, git, make, systemctl, ...)
         all still execute, in the same order, with the same arguments.
       - The main-flow sequence (critical block -> nano version probe ->
         non-critical block -> nano build block -> completions -> scripts ->
         cleanup) is unchanged.

   U3. Exit-code and error semantics
       - set -e, set -o pipefail, trap 'error_handler $LINENO' ERR.
       - run_command's fail -> log_error -> error_exit path.
       - run_non_critical's warn-and-continue semantics.
       - Every function's return value; the script's final exit code.

   U4. Interactive behavior
       - The sudo password prompt stays visible. sudo writes its prompt to
         the controlling terminal (/dev/tty), so redirecting stdout/stderr
         of wrapped commands cannot and will not hide it.

 The ONLY thing that changes is WHERE human-facing text is displayed:
 noise moves from the console into the existing log files; the console
 gains a small set of new, purely-presentational helper functions.

--------------------------------------------------------------------------------
 3. CONSOLE DISPLAY ARCHITECTURE
--------------------------------------------------------------------------------

 3.1  Core change: split the two streams

   log() drops `tee` and becomes file-only. Same line format, same target:

     Before:  echo "[$(date ...)] [$level] $message" | tee -a "$LOGFILE"
     After :  echo "[$(date ...)] [$level] $message" >> "$LOGFILE"

   Every existing log/log_error call site keeps working unmodified and the
   file log is byte-identical in format. This single edit silences most of
   the console noise with zero logic change.

 3.2  New console-only helpers (write to stdout, never to $LOGFILE)

     c_phase N "Title"   ==> [N/7] Title           (blank line before)
     c_ok    "msg"        ->   [ OK ] msg
     c_skip  "msg"        ->   [SKIP] msg
     c_warn  "msg"        ->   [WARN] msg           (ORANGE_RED color)
     c_fail  "msg"        ->   [FAIL] msg           (ORANGE_RED color)
     c_info  "msg"        ->   [INFO] msg           (progress notes only,
                                                     e.g. long nano build)

   Each badge helper also:
     - increments its counter:  COUNT_OK / COUNT_SKIP / COUNT_WARN / COUNT_FAIL
     - c_warn / c_fail additionally append the message to WARNINGS[] /
       FAILURES[] arrays for replay in the final summary block.

   set -e GOTCHA (must be respected in implementation):
     Use  COUNT_OK=$((COUNT_OK+1))   -- NEVER  ((COUNT_OK++))
     ((x++)) returns exit status 1 when the pre-increment value is 0,
     which under `set -e` would abort the script on the first badge.

   Console badge lines intentionally carry NO timestamps -- timestamps
   remain available in $LOGFILE for every underlying operation.

 3.3  Child-command output routing

   run_command() gains a file redirect around execution so uncaptured
   third-party output lands in the log instead of the console:

     eval "$cmd" >> "$LOGFILE" 2>&1          (string form)
     "$@"        >> "$LOGFILE" 2>&1          (args form)

   - Exit status of the command is unaffected; the || error path is
     untouched.
   - Commands whose strings already end in `> /dev/null` behave exactly
     as before (their inner redirect wins for stdout).
   - This captures today's console leaks: ssh-import-id's own INFO lines
     (sample lines 39-40), update-alternatives' stdout, and the apt-get
     calls inside install_1password() (:677-678) which currently have no
     redirect at all.
   - sudo's password prompt is unaffected (it prompts on /dev/tty).

 3.4  Phase structure (7 phases)

     [1/7] System preparation        set_timezone, check_updates,
                                     install_updates
     [2/7] Package installation      install_software, remove_rhythmbox
     [3/7] User environment          configure_userenv (ssh key, clock,
                                     dotfiles, sudoers/inputrc, dirs)
     [4/7] SSH & GitHub access       import_github_ssh_keys, configure_sshd
     [5/7] Applications              install_gh, install_pwsh,
                                     install_1password
     [6/7] Nano editor               remove_nano .. set_default_editor
                                     (single [SKIP] line when up-to-date)
     [7/7] Completions & scripts     setup_completions,
                                     download_standalone_scripts_api,
                                     remove_tmpfiles

   c_phase calls are inserted in the main flow only -- no function is
   reordered or moved between the critical / non-critical blocks.


--------------------------------------------------------------------------------
 4. LOOP AGGREGATION STRATEGY
--------------------------------------------------------------------------------

 4.1  Shell completions (setup_completions, :33-124)

   - Per-item `| tee -a "$error_log"` lines become file-only:
     `>> "$error_log"`. The error_log_<timestamp>.txt file keeps receiving
     exactly the same per-item content (target untouched, per U1).
   - The two loops collect names into three arrays:
       generated[]   command produced / URL downloaded successfully
       skipped[]     command not found on this host
       failed[]      generation, download, or chmod failed
   - Console output is ONE line:

       Full success / benign skips:
         [ OK ] Shell completions: 6 generated, 3 skipped (ngrok, npm, dotnet)

       Any hard failure -> WARN badge, failures listed by name:
         [WARN] Shell completions: 5 generated, 3 skipped, 1 failed (az)

 4.2  Standalone GitHub scripts (download_standalone_scripts_api, :845-882)

   - Per-file "Downloading X..." / "Successfully saved..." pairs become
     file-log-only (they already go through log(); 3.1 handles it).
   - The while-loop counts total/ok and collects failed_scripts[].
   - Console output is ONE line:

       Full success:
         [ OK ] Standalone scripts: 19/19 synced to ~/dev/scripts

       Partial failure -> explicit names on console AND per-item detail
       in $LOGFILE (existing log_error calls preserved):
         [WARN] Standalone scripts: 17/19 synced - failed: install-qemu.sh,
                install-vscode.sh

       API returned nothing (existing early-return path):
         [FAIL] Standalone scripts: GitHub API returned no download URLs

 4.3  Package install (install_software, :241-286)

   - The ~94-name package list never prints to the console. It remains in
     $LOGFILE via run_command's existing "Running command" log line.
   - Count computed at runtime:  pkg_count=$(wc -w <<< "$common_pkgs $distro_pkgs")
   - Console output:  [ OK ] Installed/verified 94 apt packages


--------------------------------------------------------------------------------
 5. WARNINGS, ERRORS & FINAL SUMMARY BLOCK
--------------------------------------------------------------------------------

 5.1  Immediate visibility

   - c_warn / c_fail print immediately, in ORANGE_RED, at the moment the
     condition is detected -- e.g. the sshd drop-in mismatch (sample lines
     43-48) becomes:

       [WARN] sshd drop-in not effective: password auth still enabled
              (check 'Include /etc/ssh/sshd_config.d/*.conf')

   - run_non_critical's generic orange warning becomes:
       c_warn "$func failed - see log"
     (its log_error call and continue-on-error semantics are unchanged).

 5.2  Nothing scrolls away: end-of-run replay

   WARNINGS[] and FAILURES[] are replayed verbatim inside the summary
   block, so a long run cannot bury a critical message.

 5.3  Elapsed time

   SCRIPT_START=$SECONDS captured at startup; elapsed computed as
   $((SECONDS - SCRIPT_START)) and formatted m/s. No external commands,
   no new dependencies.

 5.4  Summary block layout (replaces the duplicated finale, :939-940)

   ----------------------------------------------------------
    Deployment summary                        elapsed 4m 12s
    [ OK ] 13    [SKIP] 5    [WARN] 1    [FAIL] 0
    Warnings:
      - sshd drop-in not effective: password auth still enabled
    Full log: /home/cwalker-admin/temp/deploy-config_20260827_013409.log
   ----------------------------------------------------------

   - "Warnings:" / "Failures:" sub-sections appear only when non-empty.
   - The $LOGFILE path is always printed so detail is one click away.
   - The existing final `log 'All tasks completed successfully.'` line is
     KEPT (file log unchanged); only the duplicate console echo on :940 is
     replaced by this block.
